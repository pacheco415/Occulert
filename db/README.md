# Archived database source

The canonical fresh-install chain is now [`supabase/migrations`](../supabase/migrations), applied in filename order. Its `20260701000000_baseline.sql` preserves the exact ordered result of `db/schema.sql` and both `db/migrations` files. The original files remain unchanged as read-only history; put every future database change in `supabase/migrations`.

For a **new, empty Supabase project**, apply the canonical baseline once, then each later canonical migration in order. Supabase provides the `auth` schema and API roles. Do not also apply the archived files: their SQL is already embedded in the baseline. The baseline intentionally preserves overlapping invitation definitions rather than changing deployed objects.

For an **existing database**, do not run the baseline or blindly run every migration absent from the ledger. Unconditional policies and later table/index definitions can conflict with existing objects. An unrecorded version can mean SQL was previously applied manually. Preserve the current database and ledger, compare its definitions, RLS, function security/search paths, grants and foreign-key actions with the expected schema, then separately authorize any ledger reconciliation or forward repair. The baseline's older timestamp does not make it safe to replay.

If baseline equivalence is established, a project administrator can reconcile the baseline as already applied using Supabase's migration-history repair process without executing its SQL. That is an external database write requiring its own authorization; neither status utility performs it. Do not mark later migrations applied merely because their filenames appear locally. See [Supabase migration guidance](https://supabase.com/docs/guides/deployment/database-migrations) and [migration repair reference](https://supabase.com/docs/reference/cli/supabase-migration-repair).

[`docs/MIGRATION_READINESS.md`](../docs/MIGRATION_READINESS.md) describes the read-only reports and current production evidence. `npm run test:db-baseline` compares isolated legacy/canonical catalogs before fixture grants, and `npm run test:tenant-rls` exercises the complete canonical chain across tenants. PGlite supplies UUID generation directly; its tests omit only the unsupported `pgcrypto` extension installation statement. These local checks do not prove production migration coverage.
